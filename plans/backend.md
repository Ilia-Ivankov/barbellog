# Barbellog: архитектура бэкенда

## Стек и жизненный цикл

Бэкенд находится в `backend/barbellog-backend`: TypeScript, Node.js и Express 5. Сборка компилируется через `tsc`; разработка запускается через `tsx`. Требуется Node.js `>=22.13`, в частности для встроенного `node:sqlite`.

- `src/index.ts` импортирует приложение, читает `PORT` и открывает HTTP listener (по умолчанию порт `3000`).
- `src/app.ts` создаёт Express-приложение, настраивает CORS, JSON body parser, корневой health/info ответ, подключает роутеры и общую обработку 404/ошибок.
- `scripts/dev.mjs` в корне запускает миграции до старта API и Vite; остановка корневого процесса останавливает оба дочерних сервиса.

Порядок локального старта, доступные скрипты и переменные смотри в [API.md](../backend/barbellog-backend/API.md), корневом `package.json` и `scripts/dev.mjs`.

## Конфигурация

`src/config/env.config.ts` загружает `.env` через `dotenv` и задаёт:

| Переменная | Текущее значение по умолчанию | Использование |
| --- | --- | --- |
| `PORT` | `3000` | HTTP-порт |
| `SQLITE_PATH` | `./data/barbellog.sqlite` | Файл SQLite, относительный путь разрешается от текущей рабочей директории процесса |
| `JWT_SECRET` | `development-only-change-me` | Подпись токенов; в `NODE_ENV=production` требуется явное значение |
| `FRONTEND_ORIGIN` | `http://localhost:5173` | Единственный разрешённый CORS origin |

`getDatabase()` лениво открывает соединение при первом запросе к БД. При открытии включаются внешние ключи, WAL и `busy_timeout=5000`. Команда миграции открывает указанный файл отдельно и применяет SQL из `db/migrations/`.

## Маршрутизация и middleware

Базовый префикс `/api/v1` подключён в `src/app.ts`:

| Префикс | Модуль | Основное назначение |
| --- | --- | --- |
| `/auth` | `routes/auth.routes.ts` | Регистрация, вход и текущий пользователь |
| `/catalog` | `routes/catalog.routes.ts` | Общие справочники групп мышц и оборудования |
| `/exercises` | `routes/exercises.routes.ts` | Общий и личный каталог, архивирование, статистика упражнения |
| `/workouts` | `routes/workouts.routes.ts` | CRUD тренировок с вложенными упражнениями и подходами |
| `/stats` | `routes/stats.routes.ts` | Сводная статистика по группам мышц |

Порядок приложения: CORS headers и короткий ответ на `OPTIONS`, JSON parser с лимитом `100kb`, корневой `GET /`, API-роутеры, JSON 404 и `errorHandler`. `asyncRoute()` оборачивает обработчик и передаёт отклонённые Promise в Express error middleware.

Точный HTTP-контракт — методы, тела, query-параметры, примеры ответов — поддерживается в [справочнике API](../backend/barbellog-backend/API.md). При изменении маршрута обновляй оба источника.

## Аутентификация и границы доступа

- Регистрация нормализует email, принимает display name и пароль от 8 до 200 символов. Пароль хранится не в открытом виде: `scryptSync` с солью и 64-байтным результатом; сравнение при входе выполняется через `timingSafeEqual`.
- `createToken()` и `verifyToken()` реализуют подписанный HS256 JWT с `sub` пользователя и сроком жизни семь дней.
- `requireAuth` извлекает Bearer-токен, проверяет подпись и срок; `userId(req)` возвращает только установленный middleware идентификатор.
- Идентификатор владельца нельзя брать из параметров или тела пользовательского запроса. Запросы к тренировкам, личным упражнениям и агрегатам обязаны ограничиваться проверенным `userId`.
- SQLite не имеет RLS. Проверка принадлежности выполняется SQL-фильтрами и составными FK/триггерами в миграции; `withUserContext()` задаёт транзакцию, но сама по себе не обеспечивает изоляцию строк.
- Публичные маршруты справочника каталога читают общие данные; пользовательские каталоги и записи требуют `requireAuth`.

## Валидация и сериализация

`src/utils/http.ts` содержит `ApiError`, `fail()`, валидацию строк/дат/параметров, нормализацию email, адаптер `asyncRoute()` и `errorHandler`.

- Строки нормализуются Unicode NFKC и обрезаются; дата календаря проверяется как точная `YYYY-MM-DD`.
- Тренировка принимает минимум одно упражнение и минимум один подход на упражнение. Повторения — целое число в допустимом диапазоне; вес неотрицательный с точностью до `0.01` кг.
- Ошибка валидации обычно даёт HTTP 400, недействительная сессия — 401, отсутствующая/недоступная запись — 404, конфликт ограничения SQLite — 409; непредвиденная ошибка — 500 без утечки деталей клиенту.
- Успешные JSON-ответы оборачиваются в `data`; ошибки — в `error`. Удаление возвращает `204`.

## Основные операции и транзакции

### Тренировки

`workouts.routes.ts` проверяет входное тело, преобразует каждый выбранный `exerciseId` в доступное общее или принадлежащее пользователю активное упражнение, затем сохраняет тренировку, дочерние упражнения и подходы через `withUserContext()`.

`POST /workouts` создаёт запись. `PUT /workouts/:id` заменяет все вложенные упражнения и подходы целиком: сначала проверяет владельца, обновляет поля тренировки, удаляет старые дочерние записи и вставляет новые. Всё выполняется в одной `BEGIN IMMEDIATE` транзакции с откатом при ошибке. При сериализации сохраняются снимки названия, группы мышц и признака собственного веса, поэтому исторические данные не зависят от последующих изменений каталога. Удаление тренировки каскадно удаляет её дочерние записи.

### Упражнения

Каталог объединяет активные общие упражнения (`owner_user_id IS NULL`) и личные упражнения текущего пользователя. Создавать, редактировать и архивировать можно только личные упражнения владельца. Архивирование записывает `archived_at`, а не физически удаляет упражнение; архив нельзя добавить в новую тренировку.

### Статистика

`stats.routes.ts` суммирует повторы по сохранённому снимку группы мышц и объём по формуле `вес × повторы`, группируя по ISO-неделе, начинающейся в понедельник. Маршрут `exercises.routes.ts` вычисляет максимальный записанный вес упражнения по дням и недельные ряды. Упражнения с собственным весом в текущем UI записываются с внешним весом ноль; их повторы входят в статистику.

## База данных и миграции

Соединение и транзакционная обёртка находятся в `src/db/database.ts`, мигратор — в `src/db/migrate.ts`, исходная схема — `db/migrations/001_initial_schema.sql`. Текущая миграция `001_initial_schema` создаёт пользователей, справочники, упражнения, тренировки, подходы, индексы, ограничения, триггеры и стартовый набор каталога.

Для деталей полей, ключей, ограничений, снимков, точности веса и статистики используй [документацию SQLite](database.md). Новую схему добавляй отдельной версионированной миграцией; не редактируй уже применённую миграцию как способ обновить существующую локальную БД.

## Ошибки и сопровождение

Все ожидаемые ошибки маршрута должны выбрасываться через `fail()`/`ApiError`, чтобы сохранить стабильный JSON-контракт. Ошибки JSON parser и ограничения SQLite отдельно сопоставляются с кодами `INVALID_JSON` и `CONFLICT`. Неожиданные исключения логируются на сервере и клиенту возвращается общее `INTERNAL_ERROR`.

При изменении серверной логики проверь согласованность четырёх уровней: маршрут и валидация, типы/DTO клиента, API-документ и ограничения схемы. В частности, транзакция не заменяет явные фильтры владельца в SQL, а внешний ключ не заменяет проверку пользовательской доступности упражнения.
