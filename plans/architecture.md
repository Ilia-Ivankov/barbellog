# Barbellog: карта архитектуры

## Назначение и текущий состав

Barbellog — веб-приложение для личного дневника силовых тренировок. Пользователь может создавать аккаунт, записывать тренировки и подходы, вести личный каталог упражнений и смотреть статистику. Приложение состоит из React-клиента, Express API и локальной SQLite-базы. Отдельного сервиса авторизации или сервера базы данных нет.

```text
Браузер
  └─ React + TypeScript + Vite
       └─ fetch /api/v1 (Vite dev proxy → http://localhost:3000)
            └─ Express API
                 └─ node:sqlite → файл barbellog.sqlite
```

В разработке корневая команда `npm run dev` сначала применяет миграции, затем запускает API и Vite. Реальные адреса и переменные окружения описаны в соответствующих разделах ниже и в документах подсистем.

## Основные потоки данных

### Вход и сессия

1. `AuthPage` отправляет email и пароль, а при регистрации также отображаемое имя, на `/auth/login` или `/auth/register`.
2. API проверяет входные данные, читает или создаёт пользователя, хеширует пароль через Node `scrypt` при регистрации и возвращает пользователя с подписанным токеном.
3. Клиент сохраняет токен и пользователя в `localStorage` под ключом `barbellog.session`.
4. При запуске приложения клиент проверяет сохранённую сессию запросом `GET /auth/me`. При ошибке сохранённая сессия удаляется.
5. `api()` добавляет Bearer-токен к запросам, если локальная сессия существует. Сервер извлекает идентификатор пользователя только из проверенного токена.

### Запись тренировки

1. `WorkoutEditor` загружает доступный пользователю каталог упражнений; при редактировании также загружает тренировку.
2. Клиент отправляет тренировку с датой, названием, заметками и полными списками упражнений и подходов.
3. API валидирует тело и проверяет доступность упражнений. Создание или полная замена тренировки, её упражнений и подходов происходят в одной SQLite-транзакции.
4. Бэкенд сохраняет вес в сотых долях килограмма и возвращает тренировку. Клиент открывает страницу результата.

### Статистика

Клиент запрашивает агрегаты у API, передавая границы дат. Сервер вычисляет повторения, объём и недельные ряды по пользовательским тренировкам и снимкам данных упражнения, сохранённым при записи. Подробные правила расчёта приведены в [документации SQLite](database.md) и в коде маршрутов статистики.

## Важные архитектурные границы

- Фронтенд не подключается к SQLite напрямую; доступ к данным идёт через HTTP API.
- SQLite не обеспечивает row-level security. Каждый SQL-запрос к пользовательским данным должен ограничивать строки `user_id`, полученным из проверенной сессии.
- Общий каталог и личные упражнения сосуществуют. Владелец личного упражнения — один пользователь; архивирование скрывает его из нового каталога, но история тренировки хранит снимок названия и характеристик.
- API возвращает успешные ответы в `{ data: ... }`, ошибки — в `{ error: { code, message } }`; удаление обычно отвечает `204` без тела.
- В текущем интерфейсе маршрутизация реализована внутри `App.tsx` на History API; отдельная библиотека роутинга не используется.

## Область реализации

Документация описывает только возможности, обнаруженные в текущем коде. Совместные тренировки, роли тренера, программы и шаблоны тренировок, RPE/RIR и запись массы тела не входят в текущую модель данных. Не предполагай их наличие по одному лишь описанию продукта или будущим планам.
