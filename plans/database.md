# Barbellog: SQLite

## Устройство

Backend использует SQLite из встроенного модуля Node.js `node:sqlite`. База — файл `backend/barbellog-backend/data/barbellog.sqlite`; отдельный сервер, роли и сетевой адрес не нужны. Путь можно изменить через `SQLITE_PATH`. Нужен Node.js 22.13 или новее.

Начальная схема находится в [`001_initial_schema.sql`](../backend/barbellog-backend/db/migrations/001_initial_schema.sql), а `npm run db:migrate` применяет её и записывает версию в `schema_migrations`. Запускай npm-команды из папки backend. Миграция создаёт таблицы, индексы, ограничения и стартовый каталог упражнений.

## Модель

| Таблица | Назначение |
| --- | --- |
| `users` | Учётная запись, нормализованный e-mail, хеш пароля |
| `muscle_groups`, `equipment` | Общие справочники |
| `exercises` | Общий и личный каталог, основная группа мышц, оборудование, архив и признак собственного веса |
| `exercise_equipment` | Связь упражнения с несколькими единицами оборудования |
| `workouts` | Тренировка, пользователь, календарная дата, название и заметки |
| `workout_exercises` | Порядок упражнений в тренировке и снимок названия/мышечной группы/признака собственного веса |
| `workout_sets` | Порядок подходов, повторы и внешний вес в сотых долях килограмма |

Идентификаторы хранятся как UUID-строки, даты тренировок — `YYYY-MM-DD`, временные отметки — UTC ISO-строки. Вес хранится целым числом сотых килограмма: например, 72,50 кг записываются как `7250`, чтобы избежать ошибок точности чисел с плавающей точкой.

SQLite не предоставляет политики RLS. Каждый запрос к пользовательским данным обязан фильтровать по `user_id` из проверенной сессии; это особенно важно для чтения, обновления и удаления тренировок. `withUserContext(userId, callback)` задаёт транзакцию и передаёт `userId` callback-функции, но не заменяет проверки в SQL. Не принимай идентификатор пользователя из тела или query-параметров запроса.

Архивное упражнение не предлагается для новых тренировок, но записи истории остаются. FK и триггеры проверяют принадлежность тренировки пользователю, принадлежность личного упражнения и запрет добавления архива. Внешние ключи включаются при каждом открытии файла базы.

## Запуск

```powershell
cd backend/barbellog-backend
npm run db:migrate
npm run dev
```

По умолчанию файл создаётся в `data/barbellog.sqlite`. Для другого пути можно задать в `.env`:

```env
SQLITE_PATH=./data/barbellog.sqlite
```

Приложение открывает базу лениво при первом вызове `getDatabase()`; серверный маршрут-заглушка пока не обращается к ней автоматически.

## Статистика

- Максимум упражнения — наибольший внешний вес подхода. Прогресс — максимум по дате тренировки.
- Объём — сумма `weight_centi_kg * reps`, делённая на 100; повторы — сумма `reps`.
- Недельные графики группируются по понедельнику ISO-недели и дате её начала, а не только по номеру недели, чтобы не смешивать годы.
- Группировка мышц использует сохранённый снимок группы. Упражнения с собственным весом учитываются в повторах, их записанный внешний вес по умолчанию равен нулю.

## Изменения относительно PostgreSQL

Удалены PostgreSQL-сервер, `pg`, `DATABASE_URL`, роли, расширения и RLS. Сохранность пользовательской изоляции теперь зависит от обязательного `user_id` в запросах Express. Имя упражнения и e-mail нужно нормализовать на сервере перед записью (`normalize('NFKC')`, trim и lowercase); `name_key` используется для уникальности имён, включая кириллицу. Для нескольких Express-процессов один локальный файл не следует считать общей базой; в таком случае нужен управляемый PostgreSQL или отдельный SQLite-сервис/файл с корректным общим доступом.

Подходы к собственному весу, роли тренера, совместный доступ, программы, шаблоны, RPE/RIR и масса тела в MVP не хранятся.
